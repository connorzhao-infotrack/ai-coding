For Lexi — "define pre-determined"

What "pre-determined" means here

Every next-step decision is authored by us up front as rules and computed from the order's current state — never generated by a model at runtime. The suggestion still changes with the state (it's not a static list); what's fixed is the logic that chooses it. Same order state in → same next step out, every time.

It is

  • A state machine: order state → next action(s), via rules we write
  • Deterministic — identical input always gives identical output
  • State-aware — the answer differs by milestone, conditions, what's done
  • Fully unit-testable; zero token cost; instant

It is not

  • Not an LLM deciding or inventing the next step at runtime
  • Not a static list that ignores state (it very much reacts to state)
  • Not random or variable — no surprise suggestions
  • Not hard to change — the rules live in one map (see build below)

Does the chart make sense?

Yes — with one framing fix, and five things to pin down

The chart is coherent and fully pre-determined. One framing note: the legend's "count the arrows" is a helpful shorthand, but the real rule is the guard conditions — your own note proves it, since Onboarding → Provide documents is a single arrow yet is auto or a prompt depending on whether manual docs exist. So: guards decide; arrow-count is just how the chart shows it. These are the gaps I'd confirm before wiring it:

Q1

"Multiple arrows usually means prompt" — what's the exception?

The dashed "upload manual docs" is an extra arrow from Onboarding but isn't a prompt (already on screen). So we count only actions that need a prompt — confirm that rule.

Q2

Financials — exact condition gating each of Adjustments / DTP / Trust?

They loop in any order. Which are offered when? Priority order for the pills? (We're going with a fixed priority — need that order.)

Q3

"Detect missing documents" — deterministic rule or judgment?

Is there a required-docs checklist per matter, or does detecting "missing" need reasoning? This is the one spot that could need logic beyond a simple guard.

Q4

"One approval" before Settlement — a human tap?

Assuming it's an outbound/irreversible step, it always needs an explicit confirm, never auto-advance. Confirm.

Q5

Priority Notice & ELNO milestones aren't on the chart — in scope?

They exist in the render-tool catalogue but not here. Are they skipped, sub-steps, or a later addition?

The plan · main section

How we build it — a rules engine, no model

Three small pieces, mirroring the existing RenderToolCatalogue pattern. All deterministic, all testable.

1

Transition map + guards

Every milestone/state → its next action(s) and the guard conditions from the chart (onboarding pending, docs missing, invitation pending…). This is the chart, in code/config.

2

Next-step catalogue

The fixed set of real actions — each with a stable id, label (≤6 words, verb-first), actionKind (view / action / outbound) and the tool or component it fires. Mirrors RenderToolCatalogue. A pill can only ever be a real catalogue entry.

3

Resolver → typed signal

A pure function: given order state, evaluate guards → return { auto?, suggestions[] }. Emitted on turn-end & on milestone state-change. The client auto-advances or docks the pills. No LLM call anywhere in this path.

1One valid next actionnot on-screen, not outbound→ auto-float, no pill
≥2Several valid actionsa crossroad (e.g. financials)→ pills, fixed priority order
?Guarded transition"only if…"→ evaluate condition first
▣Action already on screenor purely informational→ no prompt
!Outbound / irreversibleemails, money, approval, lodgement→ always a confirm tap

At a crossroad we show every sub-step whose guard is met, in a hand-authored priority order — the most-likely one first/primary, the rest secondary. Deterministic; no ranking model needed.

Optional · not planned · parked

If we ever want the LLM to help

Everything above needs no LLM. The only thing a model could add later is polish on top of the same catalogue & signal — it would never choose the flow. Recorded here so it's not lost, but it is not part of this build.

2a · LLM re-ranks the catalogue

At a fuzzy crossroad, the model reorders the (already-valid) pills by likely intent. Still bounded by the catalogue — can't invent. Adds tokens + latency for marginal gain over a fixed priority order.

2b · LLM generates, guardrailed

The model proposes new suggestions, validated against real capabilities before showing. Most flexible, but the guardrail is a single point of failure and hardest to test / sign off. Highest risk.

Recommendation: don't, until the fixed priority order demonstrably falls short. The catalogue is doing the work, and "the model chose this next legal step" is a harder sentence to defend than "our rules did."

Appendix

Why deterministic won

The three approaches scored 0–5 on six axes. Deterministic and LLM-ranked tie on total, but they optimise opposite things — and for this feature the axes that matter (reliability, cost, testability, defensibility) all favour the rules engine. Kept here for the record.
