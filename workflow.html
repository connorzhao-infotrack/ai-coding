In-the-loop vs Send-off

Two ways to work with AI on existing code. At May-2026 capability, one wins decisively for brownfield production work — but the other already wins for greenfield POCs and isolated tickets. Here's where each fits today, with a slider you can drag to see when the math flips.

📖 Shorthand used below · context-switch · PR · AC · POC · brownfield · greenfield · one-shot rate · agent · IDE
Context-switch The mental cost of leaving one task, doing something else, and reloading the original task in your head. ~23 min typical to fully refocus. The load-bearing cost of Send-off.
CONTEXT-OUT You walk away from the work — start something else while AI is busy in the background. (Free going out — the tax is on the way back.)
CONTEXT-BACK You return to the task — pay the mental reload tax before you can usefully review what AI did.
PR Pull request. A proposed code change that needs review before merging into the main branch.
AC Acceptance criteria. The testable checklist that proves a ticket is "done."
POC Proof of concept. A throwaway prototype that tests an idea — not used by real users in production.
Brownfield Existing codebase with conventions, history, and integration surprises. Harder for AI than greenfield because hidden constraints matter.
Greenfield New code from scratch — no existing conventions to violate, no legacy integration surprises.
One-shot rate How often AI gets a ticket right on the first try, without needing to reprompt or correct.
Agent An AI process that runs autonomously — picks up a ticket from a queue, writes code, raises a PR, all without human input mid-task.
IDE Integrated development environment — your code editor (VS Code, Cursor, JetBrains, etc.).
CI Continuous integration. Automated build + test pipeline that runs on every PR.
Approach 1 · Default for brownfield production today

🧑‍💻In-the-loop

You stay in the IDE. AI is the pair, not the doer. Plan, prompt, watch the code stream in, react, reprompt — all in one continuous flow.

How it flows

PLAN → AI codes → YOU READ → REPROMPT → LOCAL TEST → PR
↺ ~2 prompt cycles average · low cost per cycle (you never lost context)
What it feels like Fast feedback. AI gets something wrong, you correct it within 30 seconds. Tests run locally on the changed code. You never lost the mental model of the task.
Tight feedback loop Low context-switch cost Serial throughput Brownfield-friendly
Approach 2 · Ahead of its time for production · ready for POCs

📤Send-off

Plan goes in a ticket. GitHub Action (or remote agent) picks it up. AI builds a PR while you're doing something else. You come back to a finished PR — or, >50% of the time, one that needs more rounds.

How it flows

PLAN in ticket → Agent picks up → Agent codes → PR raised → YOU REVIEW → REPROMPT or PULL DOWN
↺ ~2 prompt cycles average · each cycle pays a full context-switch tax
What it feels like You queued a ticket, switched to something else, ~30 min later get pinged that a PR is ready. You context-switch back, read the diff, find it half-right, leave a comment, switch away again. Pull down, run tests, find what AI missed.
High parallelism ceiling Heavy context-switch cost Async-friendly ⚠️ Brownfield-fragile today

⚠️ Reality check on the math

What the slider doesn't show

The chart is useful for direction-setting, not precision. Three real-world effects it doesn't capture — all of them shift the picture toward In-the-loop more than the math suggests.

🚧 Hidden constraints the model ignores Read before quoting the chart at people

🚦 Review bandwidth is the real ceiling

As one-shot rate climbs, the bottleneck shifts from "AI getting it right" to "human reviewing fast enough." Five parallel agents only help if you can review 5 PRs/hour without quality drop. Past a certain rate the slider says Send-off wins — but throughput hits a wall at how many PRs one person can seriously review per day.

🟡 The vigilance inversion · "lemons problem"

Counter-intuitively, 90% one-shot may be more dangerous than 50%. When most PRs look fine, reviewers relax — and the bad 10% slips through. At 50% you're vigilant; at 90% you're complacent. Multiple teams report this exact pattern with async agents in early 2026 — the bugs that ship aren't the obvious failures, they're the confident-looking subtle ones.

🔀 Most teams use both · not either/or

The decision is per-ticket, not per-team. The same engineer might Send-off five backlog tickets (lint, types, docs, simple refactors) on Friday, then sit In-the-loop Monday for the payment-flow change. The page reads as a binary worldview — in practice it's a routing decision per piece of work.

One thing that isn't a constraint →Token cost. Send-off uses more tokens per ticket (full exploration each cycle, often parallel) — but at a few cents to a few dollars per ticket, it's still trivial next to a developer hour. Cost isn't the dial; review bandwidth and vigilance are.
✅ Even today

When Send-off already wins

Approach 2 isn't a "wait until 2027" tool. At current capability, there's a real lane where its parallelism and async nature beat In-the-loop — the lane where being wrong is cheap.

🎯 The "send it" matrix · pick the right tool for the task Today's reality

📤 Send-off wins today on

  • POCs and prototypes — not used by thousands of people. If it ships broken, you throw it away and try again. Iteration cost from a bad PR is near-zero.
  • Greenfield code — no existing conventions to violate, no hidden integration surprises. AI is genuinely strong here.
  • Isolated bug fixes with clear AC and good test coverage already in place. The test suite is the safety net.
  • Doc updates, lint fixes, type annotations, dep bumps — bounded, low-risk, easy to review at a glance.
  • Codemods and refactors with a clear before/after example and tests that already cover the surface.
  • Backlog catch-up — queue 5 low-priority tickets on Friday afternoon, review the PRs Monday morning. Throughput > per-ticket efficiency.
  • Off-hours work where you genuinely are doing something else and the async loop is a feature, not a tax.

🧑‍💻 Stay in-the-loop for

  • Brownfield production work — code touched by real users, where a wrong PR causes incidents, not laughs.
  • Ambiguous tickets — anywhere "what does done look like" isn't crisply written before code starts.
  • Cross-cutting changes — touching auth, payments, schemas, contracts with other teams. High blast radius.
  • Anywhere you'd pull the PR down to test anyway — if the local-test loop is mandatory, doing it in-loop saves the whole async round-trip.
  • Subtle bugs — race conditions, flaky tests, "works locally fails in prod." AI's testing quality (~50% of human) is the rate-limiter here.
  • Anything in a regulated path — settlement, compliance, financial logic. Where being right matters more than being fast.
Heuristic →If a wrong PR costs you nothing but a delete, send it off. If a wrong PR costs you an incident, a customer apology, or a 2am page, stay in-the-loop. The cost of being wrong is the dial.
⏳ Where this is heading

When the threshold flips

For Send-off to win on brownfield production work — not just POCs — three capabilities have to climb together. None of them is far off, but none has arrived.

Three gates between today and "Send-off by default"

The slider above shows the per-ticket math flipping near 80% one-shot rate. But per-ticket math isn't the whole story — these are the three real gates that have to clear before a sensible team makes Send-off the default for production work:

  1. One-shot rate ~80%+ on real brownfield tickets · not on benchmarks. Today's ~50% means half the time you're paying full context-switch tax on a partial PR. At ~80% that tax becomes occasional, not constant.
  2. AI testing quality near human · today's ~50%. The reason teams pull every PR down locally isn't because they don't trust the agent — it's because they don't trust the agent's testing. Close that gap and the local-test round-trip stops being mandatory.
  3. AI starts asking the right clarifying questions before coding · today, agents code from whatever was in the ticket. Ambiguous ticket → wrong PR → reprompt cycle. The day agents reliably push back with "before I start, I need to know X, Y, Z" — that's the day the async loop stops bleeding cycles to ambiguity.

Honest horizon: somewhere between 6 and 36 months depending on which gate moves fastest — most likely 12–24 months for general brownfield work, longer for regulated. The exact date is a guess; the shape (these three gates, in roughly this order) is the load-bearing claim. Worth watching, not worth re-tooling your team around yet.

Bottom line · May 2026

For brownfield production work on existing repos, default to In-the-loop. The feedback loop is tighter, the context-switch cost is lower, and the cost-of-being-wrong is lower when AI gets things wrong half the time.

For POCs, greenfield prototypes, isolated low-risk tickets, and backlog catch-up, send it off. Parallelism is real value even at today's capability — as long as a wrong PR is cheap.

The threshold flips when AI's brownfield one-shot rate climbs to ~80%, testing quality nears human, and agents start asking the right clarifying questions. That's likely 12–24 months out, not next quarter. Don't rebuild your team around it yet.
