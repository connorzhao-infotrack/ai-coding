🧩 AI-Caller — Dynamic Input Form (V1 Plan)

How the file handler supplies the details each authority needs, so the AI can make the call. Draft for team review — 1 Jun 2026.

One-paragraph summary. Before the AI calls an authority it needs specific identifiers (property number, certificate number, customer reference, …). These vary by authority and most are not stored in SettleIT. The input requirements live in the InfoDialer playbook (single source of truth); SettleIT prefetches them when the adjustment page loads, so clicking Call authority opens a modal of labelled text boxes instantly — no spinner. The handler fills them in and the values are passed to InfoDialer as a JSON string (and saved against the order so a retry doesn’t need re-entry).

1 · Why we need it

🎯 The AI needs call-specific details

  • We are not doing document extraction.
  • To verify a rate, the AI must quote identifiers the authority asks for.
  • Those identifiers differ per authority (and per scenario).

🗄️ Most of it isn’t in our DB

  • SettleIT reliably stores only lot/plan (title reference).
  • Certificate number, rates account number, customer/payment reference — not stored (some “recorded in pencil”).
  • So the file handler must supply them at call time.

🧭 Keep it configurable

  • Adding a council shouldn’t need a code change.
  • The playbook already owns the call’s input definition (InputSchema).
  • Let that be the single source of truth — don’t duplicate it on SettleIT.

2 · V1 decisions (locked)

✅ Approach

  • Ask the file handler for everything the playbook requires — no auto-fill guessing in V1.
  • SettleIT fetches the field list from InfoDialer (the playbook InputSchema) — no duplicate schema stored on SettleIT.
  • Prefetch on page load — load the field list when the adjustment page opens, so the modal is instant when “Call authority” is clicked (no spinner).
  • Flatten the scenarios — one field set per playbook; cert is very likely already returned by call time, so we target the “certificate returned” case.
  • All fields are plain strings, so the form is a simple labelled-input loop — not a JSON-Schema engine.

🏷️ Labels & storage

  • Label resolution chain: schema title → small hard-coded key→label map → humanized field name (propertyNumber → “Property Number”). Good enough for a dev-only V1.
  • Persist the entered values on the order’s AdjustmentRateVerifications row (new JSON column) so a retry doesn’t require re-entry.
  • The schema itself is fetched, not stored — values are stored, definition is not.
  • Button is Dev-only (env flag), placed outside the input box.

5 · What’s already built vs new work

ALREADY BUILT  don’t rebuild

  • Outbound trigger pipe — TriggerCallRequest already has the PlaybookInputs slot; IInfoDialerApiClient.TriggerCallAsync POSTs to /api/v1/calls with machine-token auth.
  • Inbound callback receiver — ProcessInfoDialerNotificationCommand is implemented + tested (5 handler + 6 validator tests), authenticated as a SettleIT System User.
  • The two tables — AdjustmentRateVerifications (per-order) + the State/RateCategory→playbook mapping exist (SETTLEIT-10328).

NEW FOR V1

  • InfoDialer — content: populate each playbook’s InputSchema with the required fields + title labels (it’s empty today).
  • InfoDialer — endpoint: a small “get input requirements” endpoint returning a playbook’s InputSchema (the API client already exists — add a method).
  • SettleIT FE: prefetch the field list on adjustment-page load; Call-authority button (dev-flag, outside input) opens a modal that loops the fields into labelled text boxes → serialize to JSON.
  • SettleIT BE: InitiateAiCall command — validate JSON, persist on ARV, set PlaybookInputs, call the existing TriggerCallAsync.
  • Storage: add PlaybookInputs nvarchar(max) column to AdjustmentRateVerifications (retry without re-entry).

🔎 Confirmed gaps — required work (checked 1 Jun)

  • InputSchema is currently empty & unused — must be populated per playbook (with title labels) and exposed via the endpoint. This is the prerequisite for the fetch approach. NEW
  • InfoDialer doesn’t fire the callback at all (no code; CallbackUrl stored but unused) — needs callback firing + a SettleIT system-user M2M token. NEW · InfoDialer
  • No per-order “calls for this order” query on SettleIT (only the inbound write path exists) — small GetAiCallsForOrder query + FE endpoint to drive button state. NEW · SettleIT
  • Inputs → prompt is already done ✓ — BuildPromptService renders PlaybookInputs into a “Call data:” block (tested). Remaining: wire TriggerCall → prompt → realtime session (part of the live voice-call path). PARTLY BUILT

7 · Explicitly out of scope for V1

  • Auto-filling fields from the order (beyond lot/plan) — needs a per-council mapping. V2.
  • Scenario selector (“cert returned” vs “not returned” changing the field set) — V1 flattens to the cert-returned case. V2.
  • A generic JSON-Schema form engine — not needed; all inputs are flat strings rendered by a simple loop.
  • Mid-call dynamic questions (e.g. Blacktown asking “is this a new 603 cert?”) — handled by the AI live via the playbook prompt, not a pre-call form field.
