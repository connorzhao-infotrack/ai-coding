Anticipated pushback — "why not AWS Connect / Lex / Nova Sonic?"

  • AWS Connect ≠ voice AI model. It's a cloud contact-centre / telephony platform (the same layer as Telnyx and ACS, already settled in telephony-comparison.html). It doesn't replace the voice model — a real deployment uses both layers.
  • Amazon Lex is the AWS-native bot framework — intent/slot-based, materially weaker than LLM-based voice agents for unscripted operator conversations. Not in the same league as gpt-realtime / Gemini Live for this use case.
  • Nova 2 Sonic is the AWS apples-to-apples option — rated below both Gemini 3.1 and gpt-realtime-2 in the verdict above. We'd be picking a 3rd-place model when we already have to compromise to 2nd place.
🎯 Why this is a top-5 risk, not a vendor preference. The top-5 KPI lives or dies on smooth phone conversation with human council operators. Telephony is settled (Telnyx). The voice model is the only remaining quality lever. Picking a weaker model raises handoff / failure rate, which directly threatens the KPI. We're already compromising with Gemini 3.1 (Step ① of the ladder) instead of gpt-realtime-2 — dropping further to Lex / Nova Sonic isn't a sensible move when third parties already rank them lower.
💬 Honest take: I'm not very confident Gemini 3.1 Flash Live will hold up against real operators — let alone any AWS voice option. If 3.1 Flash misses the bar in eval, we should be raising step ② (exec exception), not pivoting sideways to a model the benchmarks already rate below it.

🪜 Escalation ladder — realtime voice path

Realtime voice is the only capability still without a corporate-sanctioned production path. The ladder below is the plan: try the in-flight option first, escalate to exec for a scoped exception if quality falls short, fall back to a personal-token bridge as a temporary last resort.

① Try Gemini 3.1 flash live current

  • Status: In trial via GLOBALIT-4162 (~$50/mo cap).
  • Owner: Connor + voice team.
  • What it is: Side-by-side eval of gemini-3.1-flash-live-preview vs gpt-realtime-2 as the human-agent voice. Gemini is the known weaker model — we ship with it if quality is "good enough".

Acceptable = (a) successful figure-extraction rate within 20% of the gpt-realtime-2 baseline measured on the same transcripts, (b) call duration not >50% longer, (c) human-handoff / confusion rate <30%.
  • Pros: No new approvals. Already paid for. Sustainable production path if quality holds.
  • Cons: Known to be the weaker model. May force longer calls, more handoffs.
  • Trigger to escalate: Quality bar above missed on the eval set.

Argument for the exec exception

Why the blanket policy doesn't fit here

  • The Azure-only rule exists to guarantee AU data residency for sensitive data. It's the right default.
  • But it's being applied to a workload that carries no sensitive data, and the result is an indefinite block on a model Azure AU simply hasn't shipped.
  • "A matter of time" is not a date. gpt-realtime has been GA ~8 months and still isn't in AU. We can't commit a delivery date to a region roadmap we don't own.
  • A policy meant to reduce risk is, for this use case, only adding delay — with no offsetting risk reduction.

Why AI-Caller is low-sensitivity

  • Minimal inputs: property number + address. That's the whole payload the AI needs to ask a council/water authority for figures.
  • Public-record-adjacent outputs: rates / water balances / certificate figures a human currently phones for — not confidential client data.
  • No broad PII, no credentials, no identity documents ever leave our boundary.
  • Audio is outbound-to-authority only — we're calling a public service desk, not handling a customer's private call.
  • Legal already signed off (ATIGLIT-2669): shortened disclaimer, ID anonymisation, 30-day recording retention, disclosure/consent on human-agent calls.

🚀 Bigger picture — open up direct OpenAI for safe internal workloads

The narrow case above (AI-Caller specifically) is real, but the same shape applies to other internal projects we'll build. Codifying a named-workload exception process now is cheaper than re-litigating it each time.

  1. It's an internal app with no client-sensitive data. AI-Caller sends property address + lot/plan + certificate number — public-record-adjacent data we already type into council websites by hand. No client identifiers, no documents, no credentials. (See the "Why AI-Caller is low-sensitivity" card above for the itemised detail.)
  2. Cloud providers lag the model frontier by 6–18 months, worst on "niche" infra like realtime + STT — exactly what a voice-AI product needs. gpt-realtime has been GA 8 months and still isn't in Azure AU. Right now we have no production STT path and no production access to the best realtime voice model; the blocker is Microsoft's region roadmap, not a safety problem in what we'd send.
  3. Tech-led companies don't wait for cloud parity. Stripe shipped token-based payments when they were considered risky; Figma built on WebGL/WebAssembly when both were bleeding edge; OpenAI itself ships against direct APIs no hyperscaler resells. The discipline is about what you put through new tech, not avoiding it. InfoTrack should sit on that side of the line for clearly-scoped, low-sensitivity workloads — otherwise engineers spend months building against second-best tools and the product ships degraded.
  4. Safe-by-construction, not safe-by-blocking. Direct OpenAI under enterprise terms (zero data retention, no training on our payloads) gives us the same audit / logging / data-minimisation controls we'd get through Azure — applied to a payload that was never sensitive to begin with. The Azure-only rule is the right default for sensitive data; it just doesn't earn its keep here.

The ask: a named-workload exception process for safe internal AI projects, AI-Caller as the first instance, each future addition reviewed against the same low-sensitivity criteria. Not a blanket bypass of data-residency. Guardrails + auto-revert apply.

Proposed guardrails (so the exception stays safe)

  • Scope by named workload, not blanket. Exception applies only to services on an approved low-sensitivity list — AI-Caller first; each addition reviewed.
  • Data minimisation at the boundary. The playbook sends only the fields required for the call (property number + address); nothing else is forwarded to OpenAI.
  • Enterprise terms. Use OpenAI's API under zero-data-retention / no-training enterprise terms; document this on the security review (GLOBALIT-4504).
  • Keep what's already covered on Azure. The text leg (gpt-5.4-mini) stays on AiGateway/Azure; only the realtime leg Azure AU can't serve goes direct.
  • Disclosure + retention unchanged. The legally-approved disclosure script and 30-day retention apply regardless of provider.

⏪ Auto-revert clause

Migrate the realtime voice path back behind IVoiceAIService the moment either of the following becomes true:

  • (a) Azure AU ships gpt-realtime-2 (or an equivalent realtime model). unlikely soon — gpt-realtime has been GA ~8 months and still isn't in AU; no roadmap commitment from Microsoft.
  • (b) We receive a corporate-sanctioned direct-OpenAI exception (step ② of the ladder above). realistic trigger — this is the path we actually expect to revert through.

The abstraction is already there: provider swap is a config change, no rewrite. The clause exists so a personal-token bridge (③) doesn't quietly become the permanent answer.

Bottom line for whoever approves it: we're not asking to weaken data-residency for sensitive data. We're laying out a 3-step ladder — try Gemini 3.1 first, escalate to exec for a scoped exception if quality fails, personal token as a temporary bridge if exec declines. Step ② is the sustainable answer; ③ is a transparent stop-gap with the same data path as ②, not a way around the policy. Connor is happy to raise this to whoever owns it the moment ① fails the bar.
