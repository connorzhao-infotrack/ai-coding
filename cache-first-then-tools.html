You may already have the win

The first job is not to build anything. It is to run one query and find out.

Implicit caching is on by default for every Gemini 2.5 and newer model. It needs no opt-in, no cache object, no config — it needs a stable prefix above a minimum size, and it gives you the discount automatically when it hits.

You have both conditions. The fingerprint cache in SingleAgentPromptProvider makes your prompt byte-identical call after call, and the minimum on the 3.x Flash tier is 4,096 input tokens — you are sending roughly 17,300. Four times over the line.

So the honest position is not “caching is off”. It is nobody has looked. And the two possible answers lead to completely different plans.

🔎 Two answers, two different projects

If it is hitting — the token bill you set out to cut is already ~95% smaller than the 53.2k headline implies, and most of the trimming backlog is not a cost project any more. Re-price it before anyone starts, and expect to delete items.

If it is not hitting — something is breaking the prefix, and that is a bug hunt, not a feature build. First suspect: tool-array ordering. Tools render ahead of the system prompt, so if the flattening in SingleAgentFactory iterates anything without a stable order, the prefix differs every call and nothing downstream can ever cache. That would be a one-line fix worth more than the entire build backlog.

⚠️ The trap this creates for the trimming programme

Trimming 9,000 characters saves ~4,500 tokens a turn if the cache is cold, and roughly a tenth of that if it is warm. So the same edit is either the second-best item on the list or barely worth scheduling — and you cannot tell which until you read that field.

There is a sharper edge to it. The cache has a floor of 4,096 tokens. Your stated target of “about ten pages” is ~7,500 tokens, which still clears it — but a prompt trimmed aggressively enough, on a turn with a short history, could fall under the line and lose caching altogether. Trimming is not monotonically good here. Keep the floor in view.

🤖

Flash changes the tool-count risk

The size of the model matters more to tool selection than the size of the tool list.

I told you 23 tools was comfortably fine and that count was not your problem. That was calibrated for a frontier model. On a small, fast model it is a weaker claim — Flash-tier models degrade at picking between similar tools earlier than the top tier does, and your four similarly-named trust tools are exactly the shape that goes wrong first.

It sharpens one thing in particular: consolidation moves from “good for extensibility” to “also a correctness fix”. It does not, on its own, justify stopping to build test infrastructure — see below.

📊 On the benchmark: a baseline, not a bug hunt

I originally ranked this second, arguing the gap was serious enough to close before anything else. That over-weighted a hypothetical against an observation. You are not seeing mis-selection at 23 tools, and “no reported problem” is real evidence in a way that “Flash is a smaller model” is not. Building a harness for a failure you do not have is speculative work sitting in front of two certain wins.

It sits at three instead — after the hoist, immediately before smart loading — and the reason is the sequencing, not the risk. Its job there is to capture a before reading while the tool surface is still known-good. Consolidation renames and merges tools; scoping changes which ones are present. Build the baseline after those and there is nothing clean left to compare against. The deadline was never “when it breaks” — it is “before you change the tool surface”, which is exactly where you put it.

One caveat, then it is your call. With manual, ad-hoc testing, “we do not have mis-selection” and “we have not seen mis-selection” are not the same statement. A wrong card renders like a right one; the likeliest way a tool-choice error reaches you is as a vague bug report attributed to something else. That is an argument for the baseline being genuinely informative when you do build it — not for building it sooner.

Separately: the hoist at step 2 is not behaviour-neutral either. Moving an instruction from eighteen local restatements to one global statement can change how strongly it lands. A tool-selection benchmark would not catch that — it wants a handful of conversation-level smoke tests instead. Cheaper, and a different artefact.

🧱

Why tool loading and caching are the same decision

Tools sit at position zero. Everything downstream of a change is re-processed.

🔒 The invariant worth writing down before anyone builds anything

The tool array is part of the cached prefix. Treat it as frozen per session, not per request. Everything below is designed to respect that — and it is portable, because it is a property of your own code rather than a provider feature.

🧩

Skills too — but not on a separate switch

Yes to both. One key, applied to both, or you build something worse than no filtering.

Skills are the bigger prize by a distance — 46,420 characters against 12,113 — and they are the safer thing to filter. But the two are not independent, and filtering them separately is the one arrangement that is worse than doing nothing.

⚠️ The arrangement to avoid: filtering one and not the other

Filter tools but not skills and you ship eighteen procedures that instruct the model to call tools which may not be in the request. That is not a degraded answer — it is a confidently wrong one, and on Flash it is the likeliest thing to go wrong.

Filter skills but not tools and you get the milder version: tools present with no procedure. Survivable, because the description carries some of the guidance — which is another reason step 03 matters.

Filter both on the activated milestone and the failure mode mostly disappears, because a tool is only ever absent when the procedure that would have called it is absent too. Two filters on two different keys would also double how often the cache turns over. One key.

One free thing while you are in there

The builder currently appends guardrails after the eighteen skills. Since the cache matches on a prefix, anything stable that sits behind something filtered gets thrown away with it.

❌ What is ruled out — and when to revisit

Tool search with deferred loading was my previous number three, and it is genuinely the purpose-built answer: schemas are appended rather than swapped, so it preserves the cache by design. It is also an Anthropic-API feature, and you are running Gemini 3.6 Flash. It is not available to you today, and building the extensibility story on it would contradict “able to switch providers” even if it were.

Revisit only if two things become true together: tool count passes roughly 150 after moves 1–3, and you accept a per-provider capability split. At 80 with all three done, the arithmetic above lands you under today’s footprint — so it should not come up.

The good news in “able to switch”: the discipline that matters is portable. A stable prefix with the volatile part last is what earns you implicit caching on Gemini, prefix caching on OpenAI, and an explicit breakpoint on Anthropic. Only the opt-in mechanism differs, and on your current model there isn’t one to write. Keep the invariant in your code; keep provider-specific cache plumbing out of it.

Sequence

Ordered so each step tells you whether the next one is still worth doing.

  1. 01
    today · minutes

    🧊 Read usage.total_cached_tokens

    Send the same turn twice and look at the field on the second response. Non-zero means implicit caching has been working all along and the backlog needs re-pricing before anyone starts. Zero means something breaks the prefix — go to step 02 and treat it as a bug.

    Cross-check in the chat span in the Aspire dashboard at localhost:17190 to confirm what the gateway client actually sent. Latency alone is a bad proxy — you learned that one the hard way already.

  2. 02
    today · hours

    🔒 Make the stable prefix an invariant, with a test

    Tool array frozen per session and deterministically ordered. If step 01 came back zero, the flattening in SingleAgentFactory is the first place to look — an unstable iteration order there silently costs you the entire cache, on every call, and nothing surfaces it.

    Cheap now. Expensive after someone builds request-scoped tool selection on top of a cache that was quietly working.

  3. 03
    this week · ~1 day

    ✂️ Hoist the rules, and strip the protocol from tool descriptions

    One pass: the ~9,000 characters restated across the eighteen skills, plus the measured 3,842 in the tool descriptions. It is the same protocol in two different files. Add a few conversation-level smoke tests either side — this changes how strongly an instruction lands, which a tool-selection benchmark would not catch.

  4. 04
    before you touch the tool surface · ~1 day

    📊 Build the tool-selection benchmark

    Twenty to thirty real utterances with the correct tool recorded. Not because selection is failing today — it is not — but because step 05 renames and merges tools, and afterwards there is no clean before left to measure against.

  5. 05
    then · sized by what step 01 said

    🔀 Consolidate, then scope

    Solutions 1 and 2, in that order — consolidating first means you scope a smaller, cleaner set. How much of the trimming backlog survives alongside them depends entirely on the number from step 01, which is why it is step 01.
