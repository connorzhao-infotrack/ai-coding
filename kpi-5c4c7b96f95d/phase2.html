The objective
"Leverage AI to fully automate tracking & reporting for at least two key business metrics."
The two metrics: Releases (deployment / DORA) and Support (volume + the weekly written summary). Win = maximum automation, with a human only where judgement is needed.
What happens each week — and the one place a human is needed
⏱ Weekly→ Releases from Azure DevOps · no review needed+ Read & classify the support inbox→ ✋ Human reviews the summary→ Publish to dashboard
Release data is factual — it publishes automatically. Only the AI-written support summary needs a human glance before going live. How clean that one step is becomes the main difference between the two routes below. Manual hotfix entry happens in both (hotfixes are almost always entered by hand).

The two routes

ROUTE A · GITHUB PAGES + CLAUDE ROUTINE★ LEAN / OUR PICK TO START

AI does it, git stores it

A scheduled Claude routine reads the inbox & Azure DevOps, classifies and writes the summary, and commits the data + summary to a private repo. Private GitHub Pages serves it. Manual edits are a Claude skill run locally. Review = the routine opens a Pull Request a human merges.

🔒 IT must do

  • Approve a fine-grained PAT for the routine's commits (org PAT policy)

Limitations

  • Human review = a git PR diff. Perfect audit trail, but the reviewer needs a GitHub account and reads a raw diff — fine for an engineer, clunky for a non-developer. "Pending review" on the dashboard has to be emulated.
  • Trigger is a research-preview routine (daily run caps) — add a completion check.
  • Manual entry is a skill/commit, not a polished form.
ROUTE B · AZURE FUNCTION TIMER + SMALL BACKEND

A small owned app

A timer-triggered Azure Function pulls releases (no review) and the inbox, calls the Claude API to draft the summary, and writes it as pending to a tiny store. A human approves from a Teams/Outlook card (or a small protected page); it flips to published. The dashboard reads published data.

  • The review surface — a Teams/Outlook Approve card or a tiny Entra-protected page
  • The dashboard + a proper manual admin form

🔒 IT must do

  • An Azure subscription / resource group (Function App + storage account live here)
  • A service principal for Azure DevOps + a Graph app reg for the inbox
  • M365 / Power Automate licensing if using the approval card

Limitations & notes

  • More to build & own — a backend, auth, and idempotency (avoid double-publishing on retries).
  • Bigger IT ask (service principal + Graph consent + Azure subscription).
  • Timer usually fires unattended but can occasionally stall — add an alert.
  • Good news: no complex CI/CD — deploy via VS Code / CLI / zip. Cost ≈ free Functions grant + ~$1–2/mo storage + ~$1/mo Claude API.

The deciding difference — reviewing the summary before it's published

✋ Only the AI summary needs a human. That one step is the cleanest divider.

Release/deployment numbers are factual and publish automatically in both routes. The weekly written summary is the only thing a person should glance at first — here's how that glance works in each:
Route A — approve a Pull Request

The routine opens a PR with the draft summary; a person reviews the change and merges to publish. Flawless git audit trail, but the reviewer needs a GitHub account and reads a raw diff (not the rendered summary). Great for an engineer; awkward for a non-technical approver. "Pending" must be emulated on the dashboard.

Route B — approve a rendered summary

The draft is saved as pending; the reviewer gets a Teams/Outlook card (or a small protected page) showing the rendered summary with Approve / Reject — no Git, no diffs, no new tool. "Pending review" is a first-class state the dashboard can show. This is the genuinely cleaner human step, especially for a non-developer.

Where does the AI run — Claude routine vs Claude API?

They pair naturally with the two routes, and aren't interchangeable. A Claude routine bills against your Claude subscription (no per-token fee) — but its trigger is fire-and-forget: it returns a session id, not the summary, so it must publish its own output (commit to the repo). That's Route A — and the routine even self-schedules, so an Azure timer would be redundant there. The Claude API (~$1/mo at this volume) hands the summary back in-process, so code can route it into a review queue — that's Route B (deterministic, retryable, observable). So "use the routine inside the Azure Function to cut cost" isn't really a thing: if you use the routine you don't need the Function; if you use the Function, the API is the right fit.

How to choose

Start with Route A to prove the value fast; move to Route B if/when we want a polished non-developer review workflow.

  1. Route A first — it reuses what already works (the skills), asks IT for the least (mainly: turn Actions on for the org repo), and gets a private, auto-refreshing dashboard live in days. The trade-off we accept early: the summary is reviewed by merging a PR.
  2. Graduate to Route B when the weekly reviewer is a non-developer or we want SLAs/alerting — the draft→approve-a-rendered-card→publish flow is the clean version of human review, and (good news) it needs no complex CI/CD. Bigger IT ask, a small app to own.
  3. Same dashboard, same data model either way — so moving from A to B is swapping the engine, not rebuilding. We can decide the moment based on the manager's appetite for IT setup vs. reviewer experience.
