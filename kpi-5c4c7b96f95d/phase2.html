Phase 2 — Automating the Weekly Refresh
Two ways to make the SettleIT KPI dashboard update itself every week, with no PC running. Same data, same dashboard — they differ only in who runs the weekly job.
← Back to dashboard
What gets automated each week — exactly what you do by hand today:
⏱ Weekly trigger→ Pull releases (Azure DevOps)+ Read & classify support inbox→ Write JSON store→ Dashboard updates
The only step that needs AI is classifying support emails into Task / System / User / Other-system. That single difference is what splits the two approaches.

The two approaches (the runner)

APPROACH ASIMPLE / FASTEST

Claude Code scheduled agent

A /schedule routine (remote agent) wakes weekly and runs your existing two skills, then commits the results. The agent is the classifier — no AI code to write.
⏱ Routine: Mon 7am→Claude Code remote agent
runsrelease skill → Azure DevOpssupport skill → Graph inbox
→classifies inbox natively (the skill)
→commit JSON to git repo→Static Web App auto-deploys

Strengths

  • Reuses the skills as-is — the hard part (support classification, tag-trust, conflict handling) already works.
  • Least new code — you're scheduling, not rebuilding.
  • AI classification is native & free of plumbing — no separate API/prompt to maintain.
  • Git commit = audit trail + diff review + deploy trigger in one.
  • Evolve by editing skill markdown, not redeploying infra.

Trade-offs

  • Runs on Anthropic's cloud, not Azure (fine — storage/hosting can still be Azure/git).
  • Agent reasoning is less deterministic than code; needs run-history checks.
  • Costs ~one agent session per week (tokens).
  • Still needs the Graph app registration for headless inbox access (shared).
APPROACH B

Azure Function timer

A CRON-triggered Azure Function does it all in code: pull releases, read Graph, call the Claude API to classify, write JSON to Blob. Fully serverless, fully Azure.
⏱ Timer trigger (CRON)→Azure Function
callsAzure DevOps ODataGraph inboxClaude API → classify
→write JSON to Blob Storage
→Static Web App reads JSON

Strengths

  • Fully Azure / serverless — Consumption plan is ~free at this volume.
  • Deterministic & observable — App Insights logs, retries, alerts.
  • Release pull is pure code (no LLM) — faster & cheaper.
  • Native fit with Key Vault + managed identity.

Trade-offs

  • Most code to build — port the support taxonomy into a Claude API prompt.
  • AI logic now lives in two places (skill + prompt) — risk of drift; mitigate by sharing categorisation-rules.md.
  • Manage a Claude API key (Key Vault).
  • Still needs the Graph app registration (shared).

Other areas worth mentioning

Coverage & lead time (still seeded)

Both runners should also pull code coverage and lead time for changes from Azure DevOps to replace the Phase-1 seed values. Same source either way.

Idempotency

Re-running a week must not double-count. Key support rows by weekEnding and releases by (date, application) — upsert, don't append.

Security / least privilege

Graph scoped to one mailbox; PAT read-only (Analytics); all secrets in Key Vault; managed identity for B. Rotate the currently-exposed PAT before anything ships.

Monitoring & failure alerts

B gets this natively (App Insights). A should notify on completion/failure (email/Teams) and you can eyeball the weekly commit/diff.

Human review

“Less human interaction the better” → keep only the support review step. A can open a PR with flagged items; B writes them to the review queue. Either feeds the same dashboard panel.

Effort & time-to-value

A can be live in days (reuse skills). B is a larger build but more “owned”. The shared foundation is the same work for both.

Recommendation

Build the shared foundation first, start with Approach A, migrate hot spots to B over time.

  1. Foundation (do once): Graph app registration + admin consent · Static Web App · Key Vault (rotate & store PAT) · confirm the JSON schema · pick git as the initial store.
  2. Go live with Approach A: a weekly /schedule routine runs both skills and commits JSON. You get full automation quickly, and the tricky support classification comes for free because the skill already does it well.
  3. Migrate selectively to Approach B when you want stronger SLAs/observability: move the deterministic release pull (and coverage/lead-time) to an Azure Function timer first; move support classification later once the prompt is proven. Because the foundation is shared, this is incremental — no rework.
⛳ One dependency gates either approach: the Microsoft Graph app registration with one-time admin consent for Mail.Read on the shared mailbox. Worth requesting from IT now — it's on the critical path for both.
