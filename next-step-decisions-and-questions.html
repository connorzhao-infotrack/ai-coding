⚠ External dependency — the "active action" lock

Lexi raised that while an action is live in the chat (the documents card awaiting confirm), the client arguably shouldn't be able to start something else — "grey out all the pills, and grey out the chat area until they click the buttons" — unless they cancel and abandon the task. That cancel/abandon concept doesn't exist yet (June has raised it before). This flow assumes the current behaviour: users can jump out at any time, and if they do, the follow-up prompts are exactly what brings them back. If the lock is built later, it sits above next-step rather than inside it.

Existing systems wave 2 can reuse

Manual onboarding documents — already modelled

Opting out of a consumer task is recorded as Option.IsDeleted == true. Five task types can be opted out of, each with its own "has it been provided" check:

  • VerificationOfIdentity → an identity verification exists for the consumer
  • ClientAuthorisationForm → a signed CAF exists
  • PurchaserDeclarationForm → a signed purchaser declaration exists
  • MortgageDischargeAuthorityForm → a draft MDA document exists
  • TrustAccountAuthority → a signed TAA exists

Three ready-made methods give wave 2 exactly the guards it needs: IsConsumerOnboardingConfirmedForAllConsumers (all started), AllConsumersHaveSatisfiedOnboardingRequirements (all provided), and GetConsumersWithOutstandingOnboarding (which consumers are still outstanding).

src/api/InfoTrack.SettleIt.Application/Infrastructure/BusinessLogic/ConsumerOnboarding/ConsumerOnboardingStatusLogic.cs

"Missing documents" — an existing subsystem, not a new definition

There is already an Outstanding Items engine used for agent-side reminders. Its document evaluator returns the missing document categories plus any custom documents the agent asked for but that have no file attached, and it covers VOI/CAF progress, supplier withholding, discharge authority, required client documents and approval status.

This is the natural source for the "Upload another batch of docs" guard — no new definition required, and it isn't LEAP-specific, so it works for all clients (see Q6).

…/Infrastructure/OutstandingItems/Evaluator/DocumentRelatedEvaluator.cs · Interfaces/OutstandingItems/Models/OutstandingDocumentItems.cs

"One approval" — order-level, resolved by order type

The signal is IsDocumentApproved: whether the documents required for the order's approval milestone are approved. The milestone is derived from the order type by the service — for orders with financials it's the final-approval document set. It is a single order-level flag, not per-consumer or per-party, so one approval stops the financial pills and starts "Check settlement status".

src/api/Modules/Client/…/Financials/Models/Dtos/OrderApprovalDto.cs

Adjustments detection — better than feared, one gap

The guard resolves the latest document in the SettlementAdjustments category that has a real document attached, so empty placeholders are already excluded. Crucially the pill guard and the client's viewer use the same resolver — the pill can't point at something the viewer can't open.

The gap: the code notes that draft detection is deferred, and Connor confirmed drafts do create a document row. So a saved draft would fire the pills early — the fix is to exclude drafts (see action 1).

src/api/Modules/Client/…/Financials/FinancialsService.cs → ResolveLatestCompletedAdjustmentsDocumentAsync
